# 사내 지식 자산화 여정

최근 이직한 뒤 4개월간 세 번에 걸쳐 직원들의 머릿속에만 있는 업무 지식을 자산화 하는 작업을 진행했다. 

이전에도 자료가 아예 없었던 건 아니었지만 흩어져 있거나 오래전에 최신화가 멈춰 있었다.  

## 자산화를 시작한 계기 - 코드 품질 문제

AI가 코드를 더 많이 만들어낼수록 품질은 더 중요해지는것 같다.

시간은 비용인데, 중복과 사이드이펙트는 배포를 늦춘다. 배포가 늦어지면 시간, 즉 비용이 증가한다. 

서비스가 커질수록 복리로 늘어나기 때문에 이건 비용과 직결된 문제라고 볼 수 있을거같다.

내가 입사하고 지난 4개월간 회사는 인원이 2배로 성장했고, 우리 팀이 직면한 문제는 다음과 같았다.

하나는 신규 입사자가 빠르게 늘면서 노하우를 전수할 사람이 부족해진 것이고,  
다른 하나는 AI로인해 개발자들이 코드를 만들어내는 속도가 급격히 빨라진것이다. 

생산량은 늘었는데 검수할 사람은 한정적인 문제가 발생했다.
그러다보니 컨벤션, 도메인 지식, 비즈니스 룰, 맥락이 없는 코드가 배포되거나, 아니면 리뷰가 병목이 되는 문제가 발생했다.

그래서 품질을 준수할 수 있도록 코딩 컨벤션, 도메인 지식, 비즈니스 룰, 용어 사전을 만들어야겠다고 생각했다.

## 첫 번째

먼저 컨벤션 문서를 만들었다. 

**컨벤션 문서를 만들때는 외부의 컨벤션 문서를 그대로 적용하는 대신 회사에서 이미 암묵적으로 지켜오던 패턴을 발굴했다.**

절차는 네 단계였다.

1. **표본 선정.** 회사에서 잘한다고 인정받는 사람
2. **기존 문서 참고.**
3. **준수 여부 측정.** 그 문서를 실제로 따르고 있는지, 아니면 각자 자기 방식으로 개발하고 있는지 검토
4. **차이 해소.** 개발자별로 다른 부분, 다르면 어느 쪽이 더 나은지 검토

4번의 판정 기준은 논란의 여지가 생기지 않도록 최대한 개인적인 주관과 취향을 배제한 채 **외부에 많이 알려진 베스트 프랙티스를** 참고했다.

### 여전히 해소되지 않는 문제

문제는 만들어진 코딩 컨벤션, 비즈니스 룰, 도메인 지식, 용어 사전을 전부 숙지하기에는 내용이 너무 방대했다.  
신규 입사자가 그 많은 내용을 짧은 시간안에 전부 이해한채로 개발하는 건 사실상 불가능했다.  

## 두 번째

결국 인간이 실수하더라도 시스템 수준에서 자동으로 막아줘야 한다고 생각했고, 깃허브 액션을 떠올렸다.

PR을 올리면 정적 분석 도구로 기계적으로 검사해서 막는 것과 Code Rabbit, Claude Code Review 같은 LLM 리뷰 도구를 붙이는 것이 후보였다.

정적 검사는 문법과 스타일은 잡더라도 도메인과 비즈니스 룰을 이해하지 못하기 때문에 맥락과 사이드이펙트는 여전히 놓칠 수 있었다.  
그래서 정적분석과 LLM을 함께 사용하는 하이브리드 방식으로 방향을 잡았는데, 막상 적용하려니 다음과 같은 절차가 남아있었다.

도구별 비용 조사, 장단점 비교, 트레이드오프 정리, 제안, 품의, 결제, 제품 사용법 습득, 권한 신청, 계정 관리, 문서화.  
그제서야 제대로 사용해 볼 수 있게 되고 실제로 운영에 적용이 가능한지 검증할 수 있게 된다. 그러고나서 안정화 시키는동안 튜닝 n회.

나는 단지 리뷰봇 하나 붙이고 싶었을 뿐인데 과정이 너무 길고 복잡하다는 생각과 시간이 너무 오래걸릴거같다는 생각이 들었다.

### 본질적 복잡성과 우발적 복잡성 분리

두 가지를 분리했다.

- **본질:** 리뷰가 되게 하는 것
- **우발:** 어떤 도구를 쓸 것인가

정적 분석이냐 Code Rabbit이냐 Claude Code Review냐는 전부 How다.  
그래서 **도구 도입 결정과 문제 검증을 분리했다.** 

문제 검증은 내 로컬 PC에서도 간단하게 가능했다.  
로컬에서 내 클로드 코드로 PoC를 진행했다. 덕분에 한 달 넘게 걸릴 수 있는 코드 리뷰 자동화를 반나절 만에 검증했다.  
본질적인 문제였던 리뷰를 자동화해서 리뷰 병목을 해소한다는 목적을 달성했기 때문에 새로운 도구 도입과 비용 결제 없이(물론 내 개인 클로드 토큰을 사용하는거기는 하지만) 바로 로컬 리뷰 봇을 사용해서 목적을 달성할 수 있었다.  

리뷰봇은 지금도 내 로컬에서 운영되고 있다. 10분마다 도는 루프로 리뷰봇은 지난 PR 이력을 추적하여 연계 작업이 있는지, 이 작업의 목적과 배경, 사용자가 체감하는 변경 부분, 비즈니스 동기, 기술 요약, 변경내용, 주요변경사항, 영향 범위, 사이드이펙트, AS-IS TO-BE 시퀀스 다이어그램, 테스트 방법, 잘한점, 수정이 필요한부분 개선을 제안하는 부분, 컨벤션이 지켜졌는지, 종합 판단을 제공하고 있다.

물론 내 로컬 컴퓨터에서만 돌아가기때문에 여러 불편함을 상상할 수 있겠지만 아직까지는 그 불편함이 회사에서 비용을 들여서 새로운 도구를 도입하고 관리할만큼의 필요성을 불러 일으키지는 않는것같다. 물론 서비스의 규모와 중요도에 따라서 정석적이고 꼼꼼하면서 절차를 거쳐야하는 방식이 필요한 때도 있을것이다.  

### 여전히 해소되지 않는 문제

문제는 리뷰봇을 도입하고나서도 여전히 머지는 오래 걸리고 컨벤션은 지켜지지 않으며 사이드이펙트를 품은 코드는 계속 배포되고있었다.

리뷰봇이 못 잡아서가 아니라 **잡는 시점이 너무 뒤에있는게 문제였다.**

PR을 올리면 리뷰를 하고, 리뷰에서 수정할 부분이 보이면 고친다. 고치고 다시 올리면 다시 리뷰를 한다.  
품질이 보장되지 않은채로 PR이 올라오고 그걸 리뷰로 교정하는 방식으로 사이클이 진행되다보니 어떤 PR은 머지되는데까지 3일 이상 걸리는 경우도 발생했다.  

결국 컨벤션도 리뷰자동화도 수단이었고 본질은 코드 품질이었다. 코드 품질을 개선하기에는 문서와 리뷰봇의 사후 교정으로는 부족했다.

## 세 번째

그래서 관점을 바꿨다. 어떻게 하면 AI로 코드를 만들어내는 시대에 코드 품질을 유지할 수 있을까.

사람이 찾아 읽을 문서도 아니고 사후에 검사하는 방식도 아닌, **AI가 코드를 작성하는 순간부터 품질을 유지할 수 있도록** 하네스를 만들어야겠다는 생각을 했다.

코드 품질을 높히기 위해 아래의것들을 만들었다.

- DB 컨벤션
- 백엔드, 프론트엔드, CSS 컨벤션
- 디자인 규칙
- 도메인 지식
- 비즈니스 룰
- 상태 전파 조건
- 아키텍처
- 용어사전
- 개발자용 Claude Code 하네스
- 프로젝트 별 하네스

그리고 개발자와 비개발자를 대상으로 AI 활용 세미나를 진행하며 활용 방법과 노하우를 공유했다.  

비로소 품질 문제가 어느정도 해소된거 같기는 했지만 여전히 부족한 부분이 있다고 느껴졌다.  

코드는 언제나 단일 진실 공급원(SSoT)이고 문서와 하네스는 낡는다.  
낡는것과 시간이 지나도 유지되는것을 레이어를 나눠서 관리해야한다.  
그리고 무엇보다 자산화 하는것보다 자산화한 걸 계속 최신화 하는게 문제였다.  

그렇다면 의존성을 역전해서 문서와 하네스가 단일 진실 공급원이고 코드가 부산물이 되게 한다면?  
맞는 비유인지는 모르겠지만 예전에 프로덕션 코드와 견고하게 만들어진 테스트 코드가 있는데 둘중에 하나를 골라야한다면 테스트 코드를 골라야한다는 내용을 들었던 기억이있다.  
왜냐하면 테스트 코드에 비즈니스 정책과 도메인 룰이 있기 때문에 프로덕션 코드가 없어도 테스트 코드의 정책과 도메인 지식을 바탕으로 프로덕션 코드를 재현할수있지만,
프로덕션 코드만 남고 테스트 코드가 없으면 해당 프로덕션 코드를 신뢰하기 힘들기 때문이라는 맥락의 내용이었던걸로 기억한다.  
결국 이런식으로 테스트 코드처럼 문서와 하네스가 단일 진실 공급원이 되어서 언제든지 동일한 품질의 제품을 만들어 낼 수 있으려면 혼자만의 힘으로는 불가능하다.  
하네스의 정책으로 최대한 최신화를 강제하면서도 팀원들의 자발적 참여와 공유, AI First Development를 할 수 있는 문화와 역량이 정착되어야한다고 생각한다.  
구성원들이 오너십을 가지고 자발적으로 Knowledge Base를 갱신하고 구축하는데 참여하도록 만들 수 있게 하는것이 다음 미션이라고 생각된다.  
그러려면 더 작은단위로 프로젝트를 분리해서 개개인에게 책임지도록 맞겨야하는걸까? 그러면 버스팩터를 관리하기 위해 자산화가 잘되는지 모니터링을 해야할수도 있다.  
그런데 이게 지금 규모에서 맞는건지도, 아예 방향을 잘못 잡고있는걸지도 모르겠다.  
아직까지는 세미나라던지 공유를 통해서 활용 방법을 공유하고 동기 부여를 하는식의 방법밖에는. 뾰족한 수가 떠오르지는 않는다.

### 딜레마

문화라는건 강제한다고 생기는것도 아니고 그렇다고 방치할수도 없는 어려운 문제인거같다.  

세미나도 발표 순번을 정하면 참석률은 오르겠지만 그 순간 세미나는 업무가 되고 순번이 다가온 사람은 억지로 때우려 한다.  
평가에 반영하는 것도 순번제도 같은 함정인것 같다. 자발성을 보상하려는 순간 자발성이 아니게 된다.   

결국에는 여러 방법이 있을것같다. 처음부터 성장 가능성과 역량이 있는 인재를 찾아서 잘 채용하는것, 그리고 그 사람이 떠나지 않고 계속 기여할 수 있도록 적절한 보상과 미션을 주는것.

새로 입사하는 사람의 경우에는 어느정도 처음부터 교육을 통해서 만들어 낼 수 있을 가능성이 높기 때문에 비교적 수월 할 수 있지만, 기존에 있던 사람들을 변화시키는건 어떻게 해야할까?

기존의 인원들에게 동기부여를 하고 지속가능한 문화를 만들고 혁신을 이뤄내는것은 정말 어려운 부분인거같다.
